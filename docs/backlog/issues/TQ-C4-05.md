# [TQ-C4-05] Garantir la reprise sans double effet du traitement asynchrone (enabler à valider)

- Roadmap Cycle: 4
- Roadmap Position: S23 (position 5 du cycle 4)
- Primary Roadmap Topic: S23 Garanties de traitement (at-least-once, doublons, idempotence, retry, DLQ, poison messages)
- Secondary Roadmap Topics: S5 Concurrence ; S16 Transactions ; S18 Reprise batch ; S26 Observabilité
- Functional Capability: `UNKNOWN / TO VALIDATE` — dépend de TQ-C4-03 ; candidat : ne jamais notifier deux fois, ne jamais perdre une notification, ne jamais bloquer le flux sur un message invalide
- Nature: RELIABILITY
- Maturity: `OUTLINE`
- Dependencies: TQ-C4-04
- Context Summary: Un consommateur asynchrone peut être arrêté, redémarré ou redistribué au milieu d'un traitement ; la livraison est au moins une fois.
- Problem Summary: `UNKNOWN / TO VALIDATE`. Après un crash, les messages non validés sont rejoués : un participant reçoit deux fois la même notification ; un message malformé bloque indéfiniment la partition ; un échec transitoire n'est jamais réessayé, ou l'est sans limite.
- Objective: Si validé : consommateur idempotent, politique de réessai bornée, file de rebut pour les messages empoisonnés, démonstration de la reprise après crash sans double effet ; explication de pourquoi « exactly once » ne suffit pas.
- Expected Outcome: Si validé : le crash d'un consommateur puis sa reprise ne produisent ni perte ni doublon observable. Ce n'est pas une décision architecturale approuvée.
- Expected Evidence: Crash et reprise démontrés ; test d'idempotence du consommateur ; message empoisonné routé ; ou décision humaine documentée.
- Topics Explicitly Deferred: Cohérence entre base et messagerie côté producteur (TQ-C4-06).
- Unknowns: `UNKNOWN` support de déduplication ; `UNKNOWN` politique de rebut ; `UNKNOWN` devenir si TQ-C4-03 n'est pas validé.

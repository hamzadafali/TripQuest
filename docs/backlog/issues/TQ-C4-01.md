# [TQ-C4-01] Stabiliser le contrat de l'API TripQuest : OpenAPI, versionnement, pagination, idempotence, Problem Details

- Roadmap Cycle: 4
- Roadmap Position: S19 (position 1 du cycle 4)
- Primary Roadmap Topic: S19 APIs robustes (REST, OpenAPI, versioning, pagination, idempotency keys, Problem Details)
- Secondary Roadmap Topics: S9 Spring Web ; S12 Sécurité (exposition du contrat) ; S15 Pagination côté base ; S25 Tests de contrat
- Functional Capability: tous les modules exposés ; parcours 2 (invitation) et 3 (proposer et voter) en présence de réessais client
- Nature: FEATURE
- Maturity: `OUTLINE`
- Dependencies: TQ-C2-03, TQ-C3-04
- Context Summary: L'API sert les parcours du MVP mais sans contrat formel. Un client (UI ou test) qui réessaie après un timeout peut créer deux voyages ou deux propositions ; les erreurs n'ont pas de format uniforme ; les listes ne sont pas paginées côté API.
- Problem Summary: Créations dupliquées sur réessai ; erreurs hétérogènes et inexploitables par un client ; aucun contrat vérifiable ni stratégie d'évolution ; listes non bornées.
- Objective: Contrat OpenAPI généré et validé, erreurs au format Problem Details, clés d'idempotence sur les opérations de création, pagination exposée pour les listes, stratégie de versionnement décidée par ADR.
- Expected Outcome: Un réessai d'une création avec la même clé ne crée rien de plus ; toute erreur porte un type, un titre et un détail exploitables ; le contrat est publié et testé.
- Expected Evidence: OpenAPI validée en test ; tests Problem Details ; test d'idempotence de création ; tests de pagination ; ADR versionnement.
- Topics Explicitly Deferred: Résilience des appels sortants (TQ-C4-02) ; messagerie.
- Unknowns: `UNKNOWN` stratégie de versionnement ; `UNKNOWN` durée de conservation des clés d'idempotence ; `UNKNOWN` opérations naturellement idempotentes (accepter, voter) nécessitant ou non une clé.

# [TQ-C3-05] Faire évoluer le schéma de TripQuest sans interruption ni perte (expand/contract)

- Roadmap Cycle: 3
- Roadmap Position: S17 (position 5 du cycle 3)
- Primary Roadmap Topic: S17 Migrations (Flyway, expand/contract, zero-downtime migration, backfill, mixed versions)
- Secondary Roadmap Topics: S13 Modélisation ; S27 CI/CD (migrations en pipeline) ; S28 Déploiement (rollback)
- Functional Capability: transversale — continuité de service lors d'un changement de modèle
- Nature: DATA
- Maturity: `OUTLINE`
- Dependencies: TQ-C3-01
- Context Summary: Le schéma est versionné depuis TQ-C3-01. Un changement de structure réel est nécessaire (candidat à choisir au début du ticket : par exemple rôle de coorganisateur, séparation date/heure d'une activité, ou autre besoin apparu) alors que deux versions de l'application peuvent coexister pendant un déploiement.
- Problem Summary: Une migration destructive appliquée d'un coup casse l'ancienne version encore en cours d'exécution ou perd des données ; un backfill sur une table volumineuse bloque les écritures ; aucune procédure ne garantit la compatibilité entre deux versions.
- Objective: Réaliser le changement retenu en phases expand / migrate / contract, avec backfill non bloquant, et prouver que l'ancienne et la nouvelle version fonctionnent contre le schéma intermédiaire.
- Expected Outcome: Le changement est appliqué sans interruption ni perte, avec une procédure réutilisable pour les évolutions futures.
- Expected Evidence: Migrations en phases ; test versions mixtes ; backfill mesuré ; procédure documentée.
- Topics Explicitly Deferred: Rollback applicatif orchestré (TQ-C5-04).
- Unknowns: `UNKNOWN` changement de schéma servant de support ; `UNKNOWN` mode de simulation des versions mixtes ; `UNKNOWN` outil de migration (Flyway est le candidat de la roadmap).

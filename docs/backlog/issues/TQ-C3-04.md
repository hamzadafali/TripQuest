# [TQ-C3-04] Garder le tableau de bord et les listes de propositions rapides à grande échelle

- Roadmap Cycle: 3
- Roadmap Position: S15 (position 4 du cycle 3 dans ce backlog ; placé après S16)
- Primary Roadmap Topic: S15 SQL et performance (index, sélectivité, statistiques, EXPLAIN ANALYZE, pagination)
- Secondary Roadmap Topics: S2 (complexité) ; S14 JPA ; S26 Observabilité (temps de requête)
- Functional Capability: tableau de bord « mes voyages » (écran 2), liste des propositions avec scores (écran 6), espace de vote (écran 8)
- Nature: DATA
- Maturity: `OUTLINE`
- Dependencies: TQ-C3-02
- Context Summary: Les vues chargent un nombre de requêtes maîtrisé, mais rien ne garantit que chaque requête reste rapide quand le nombre de voyages, de propositions et de votes grandit.
- Problem Summary: Le tableau de bord filtre par appartenance ; la liste des propositions trie par score ; sans index adaptés et sans pagination, ces requêtes parcourent des tables entières ; aucun jeu de données réaliste n'existe pour le constater.
- Objective: Jeu de données généré à une échelle définie, requêtes clés analysées avec EXPLAIN ANALYZE, index justifiés par la sélectivité, pagination des listes, diagnostic et correction d'au moins une requête lente.
- Expected Outcome: Les requêtes du tableau de bord et des listes de propositions restent bornées en temps sur le volume cible ; les listes sont paginées de façon stable.
- Expected Evidence: Plans EXPLAIN ANALYZE avant/après ; index documentés avec leur justification ; tests de pagination ; générateur de données.
- Topics Explicitly Deferred: Pagination exposée dans le contrat d'API (TQ-C4-01) ; métriques de temps de requête en production (TQ-C5-02).
- Unknowns: `UNKNOWN` volumes cibles (voyages, propositions, votes par voyage) ; `UNKNOWN` pagination par curseur ou par décalage ; `UNKNOWN` score calculé à la volée ou matérialisé.

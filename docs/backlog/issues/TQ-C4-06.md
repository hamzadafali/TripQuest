# [TQ-C4-06] Choisir et prouver la stratégie de cohérence entre base et messagerie (enabler à valider)

- Roadmap Cycle: 4
- Roadmap Position: S24 (position 6 du cycle 4)
- Primary Roadmap Topic: S24 Cohérence distribuée (dual write, Transactional Outbox, Saga, compensation, réconciliation)
- Secondary Roadmap Topics: S10 Transactions ; S16 ; S23 ; S30 Architecture
- Functional Capability: `UNKNOWN / TO VALIDATE` — dépend de TQ-C4-03 ; candidat : une décision validée en base doit finir par produire sa notification, jamais l'inverse
- Nature: TECHNICAL ENABLER
- Maturity: `OUTLINE`
- Dependencies: TQ-C4-05
- Context Summary: Si une décision écrit en base et publie un message, les deux écritures ne sont pas atomiques : l'une peut réussir sans l'autre.
- Problem Summary: `UNKNOWN / TO VALIDATE`. Une décision enregistrée sans message publié laisse les participants sans notification ; un message publié sans décision enregistrée annonce une décision inexistante ; aucune réconciliation ne détecte l'écart.
- Objective: Si validé : reproduire le problème de double écriture, comparer transaction locale, Outbox, Saga et réconciliation pour le cas TripQuest, retenir la solution la plus simple qui tienne, la démontrer et la documenter par ADR. Le MVP n'exige aucune Saga.
- Expected Outcome: Si validé : après une panne entre la base et la messagerie, l'écart est résorbé sans intervention manuelle. Ce n'est pas une décision architecturale approuvée.
- Expected Evidence: Double écriture reproduite ; solution démontrée sous panne ; ADR de choix ; ou décision humaine documentée.
- Topics Explicitly Deferred: Aucun.

# [TQ-C2-06] Rendre atomiques et traçables les décisions de l'organisateur (clôture, sélection, finalisation, réouverture)

- Roadmap Cycle: 2
- Roadmap Position: S10 (position 6 du cycle 2 dans ce backlog ; déplacé en fin de cycle)
- Primary Roadmap Topic: S10 AOP et transactions (proxies, self-invocation, propagation, rollback, isolation, transaction boundaries)
- Secondary Roadmap Topics: S13 Modélisation PostgreSQL (premier support transactionnel) ; S16 Transactions et concurrence ; S22 Contrats événementiels (faits métier émis par les décisions)
- Functional Capability: traçabilité (AC-10 MVP), décisions de l'organisateur (Modules B, D, E, F), base des notifications (§7)
- Nature: RELIABILITY
- Maturity: `OUTLINE`
- Dependencies: TQ-C2-05
- Context Summary: Les décisions de l'organisateur enchaînent plusieurs effets (changer un état, tracer l'acteur, préparer une notification). Tout est encore en mémoire et disparaît au redémarrage ; la trace des décisions est réalisée à la main dans chaque opération.
- Problem Summary: Une décision peut être appliquée partiellement si un effet échoue ; la trace est dupliquée et oubliable ; un aspect ou une transaction déclarés sur une méthode appelée en interne ne s'appliquent pas silencieusement (self-invocation) ; sans support transactionnel réel, le rollback ne peut pas être démontré.
- Objective: Frontières transactionnelles définies au niveau des opérations métier ; trace des décisions appliquée de façon transversale et fiable ; pièges des proxies connus et évités ; premier support transactionnel introduit avec le périmètre minimal nécessaire à la démonstration (`PROPOSED` : PostgreSQL minimal, à confirmer).
- Expected Outcome: Une décision échoue entièrement ou réussit entièrement ; la trace acteur / date / action existe pour toute décision importante ; une décision validée n'est jamais annulée par l'échec d'une notification (§7).
- Expected Evidence: Test de rollback sur échec au milieu d'une décision ; test démontrant puis évitant le piège de self-invocation ; règles de propagation documentées ; frontières transactionnelles listées.
- Topics Explicitly Deferred: Modélisation relationnelle complète (TQ-C3-01), JPA (TQ-C3-02), verrouillage en base (TQ-C3-03), mécanisme de livraison des notifications (cycle 4, à valider).
- Unknowns: `UNKNOWN / TO DECIDE` introduction de PostgreSQL ici (périmètre minimal recommandé) ou en TQ-C3-01 ; `UNKNOWN` trace par aspect ou par appel explicite ; `UNKNOWN` émission de faits métier depuis les décisions dès ce ticket.

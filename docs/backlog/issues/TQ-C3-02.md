# [TQ-C3-02] Charger les vues du voyage avec JPA/Hibernate sans surprise (N+1, fetch, dirty checking)

- Roadmap Cycle: 3
- Roadmap Position: S14 (position 2 du cycle 3)
- Primary Roadmap Topic: S14 JPA/Hibernate (persistence context, dirty checking, fetch plans, N+1, batching, locking)
- Secondary Roadmap Topics: S1 (tension entre modèle immuable et entités gérées) ; S15 SQL et performance
- Functional Capability: vue générale du voyage, liste des participants, liste des propositions avec scores, itinéraire (écrans 4 à 10)
- Nature: DATA
- Maturity: `OUTLINE`
- Dependencies: TQ-C3-01
- Context Summary: Le schéma existe. L'accès aux données doit servir des vues agrégées (un voyage, ses participants, ses propositions, leurs scores, ses journées) sans exploser en requêtes.
- Problem Summary: Une vue du voyage naïve déclenche une requête par participant, par proposition et par vote (N+1) ; le cycle de vie du persistence context (chargement, modification implicite, flush) est invisible et produit des écritures inattendues ; le modèle immuable du noyau et les entités gérées par Hibernate ne coexistent pas sans décision.
- Objective: Plans de chargement explicites pour chaque vue, nombre de requêtes maîtrisé et vérifié par test, cycle de vie du persistence context documenté, décision sur la relation entre noyau métier et entités persistées.
- Expected Outcome: Chaque écran du MVP charge son voyage en un nombre de requêtes borné et connu ; aucune écriture n'est déclenchée par une simple lecture.
- Expected Evidence: Assertions sur le nombre de requêtes par vue ; fetch plans documentés ; batching démontré ; note sur la séparation noyau / entités.
- Topics Explicitly Deferred: Verrouillage optimiste/pessimiste (TQ-C3-03) ; index et EXPLAIN (TQ-C3-04).
- Unknowns: `UNKNOWN` mapping direct du noyau ou modèle de persistance séparé ; `UNKNOWN` usage de projections pour les vues en lecture ; `UNKNOWN` opportunité de JPA pour tous les modules ou seulement certains.
